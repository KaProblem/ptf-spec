# Personal Tutor Format (PTF)

**Version 0.1 (draft)**

PTF is an open format for **learning content that an AI tutor can teach from**:
concepts explained at several difficulty levels, question blocks, learning
paths, and versioned interactive simulators. It is designed to be authored by
people, generated by agents, shared as plain files in Git, and taught in a way
that is always tailored to the individual learner. That last part is what the
"Personal" in the name stands for: the content is open, the explanation is
personal.

PTF is a **profile of the [Open Knowledge Format (OKF) v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)**.
Every PTF bundle is a valid OKF bundle: a directory of Markdown files with
YAML frontmatter. PTF fixes a small set of `type` values, frontmatter fields
and body headings, and adds two things OKF does not cover: question blocks
and simulator packages.

Companion documents:

- [SIMULATOR-SPEC.md](SIMULATOR-SPEC.md): simulator packages, the host
  contract, build rules and security.
- [LEARNER-RECORD.md](LEARNER-RECORD.md): the portable, private learner
  profile and progress format.
- [schemas/](schemas/): JSON Schemas for everything machine-checkable.

The key words MUST, SHOULD and MAY are used as in RFC 2119.

## 1. Design goals

1. **Plain files.** Readable without tooling, diffable in Git, portable.
2. **Agent-first, human-reviewable.** Most content will be drafted by agents;
   provenance and review status are first-class (inherited from OKF).
3. **Material, not a script.** A learning element gives the tutor facts,
   anchors, misconceptions and questions. The tutor writes the actual
   explanation for each learner. Ready-made texts are optional.
4. **Levels everywhere.** Every concept can be explained to a child, a high
   school student, a college student and an expert.
5. **Self-contained lessons.** Content MUST NOT assume the learner has seen
   the source material (a video, a paper). Sources are grounding only.
6. **Reproducible interactivity.** Simulators are immutable, versioned
   packages that content refers to by ID and version range.
7. **Learner owns their data.** Progress lives in a learner record that is
   local and private by default (see LEARNER-RECORD.md).

### Non-goals

- A runtime, LMS or user interface. PTF is a format; hosts (an agent with
  an MCP server, a web app, a CLI) decide how to present it.
- Replacing assessment standards such as IMS QTI. PTF question blocks are
  deliberately small and can be converted.

## 2. Terminology

| Term | Meaning |
| --- | --- |
| Library | A collection of bundles and simulators, usually one Git repository. |
| Bundle | A self-contained topic area (e.g. "How LLMs work"). An OKF bundle. |
| Learning Element | One concept, explained at several levels. One Markdown file. |
| Learning Path | An ordered sequence of learning elements towards a goal. |
| Question Block | One quiz item of a catalogued kind, as JSON. |
| Simulator | A versioned, sandboxed HTML/JS package that lets the learner explore a concept. |
| Level | A difficulty level (§5). |
| Host | Software that presents PTF content and runs simulators. |
| Tutor | The agent (or person) teaching from PTF content. |
| Learner Record | A learner's private profile and progress (LEARNER-RECORD.md). |

## 3. Library and bundle layout

```
library/
  README.md
  sims/                           # shared simulator packages
    <sim-name>/
      <version>/                  # immutable once published
        sim.json
        index.html
        ptf-sim.js
        test.json                 # optional self-test
  bundles/
    <bundle-name>/
      index.md                    # REQUIRED for PTF: bundle metadata
      log.md                      # optional, OKF update history
      ptf.lock                    # optional, pinned simulator versions
      elements/
        <element>.md              # type: Learning Element
      paths/
        <path>.md                 # type: Learning Path
      sims/                       # optional, bundle-local simulators
```

- A bundle MAY live on its own (outside a library); it then carries its
  simulators in `<bundle>/sims/`.
- Resolvers look for a simulator first in `<bundle>/sims/`, then in the
  library's `sims/`, then in a configured registry (§8).
- `index.md` and `log.md` are reserved filenames (OKF §3.1).

### 3.1 Bundle `index.md`

```yaml
---
type: Bundle
okf_version: "0.2"
ptf_version: "0.1"
id: llm-basics
title: How large language models work
description: From next-character prediction to self-attention, built up step by step.
lang: en
license: CC-BY-SA-4.0
version: 0.1.0
levels:                 # optional: custom levels in addition to the defaults (§5.2)
  - id: practitioner
    rank: 2.5
    description: Working developers without a math background.
---
```

The body lists the bundle's paths and elements for progressive disclosure,
as in OKF §8.

## 4. Identifiers

| Thing | Local ID | Global ID |
| --- | --- | --- |
| Learning element | path within the bundle without `.md`, e.g. `elements/softmax` | `ptf:el/<bundle>/<name>`, e.g. `ptf:el/llm-basics/softmax` |
| Learning path | `paths/<name>` | `ptf:path/<bundle>/<name>` |
| Simulator | `<sim-name>` | `ptf:sim/<sim-name>` |
| Simulator version | | `ptf:sim/<sim-name>@<semver>` |
| Simulator station | | `ptf:sim/<sim-name>@<semver>#<station>` |
| Question block | `id` field, unique within its element | `ptf:el/<bundle>/<name>#<question-id>` |
| Level text | | `ptf:el/<bundle>/<name>#level/<level>` |

Names are lowercase ASCII, digits and hyphens (`^[a-z0-9][a-z0-9-]*$`).
Scoped simulator names for personal forks MAY use `ptf:sim/@<scope>/<name>`.

## 5. Levels

### 5.1 Default levels

| Rank | ID | Audience | Explanation style |
| --- | --- | --- | --- |
| 1 | `child` | Primary school, about 7 to 10 years | Pictures, everyday analogies, no formulas |
| 2 | `highschool` | Secondary school up to final exams | Intuition plus simple numbers, school math |
| 3 | `college` | Undergraduates, interested practitioners | Formulas, code, derivations |
| 4 | `expert` | Graduate students, professionals | Limits, variants, current research |

A learning element MUST cover at least two levels and SHOULD cover adjacent
ones, so a tutor can step up or down.

### 5.2 Custom levels

A bundle MAY define additional levels in its `index.md` under `levels`, each
with an `id` and a numeric `rank`. Consumers MUST order unknown levels by
rank and MUST NOT reject them.

## 6. Learning Element

One file per concept, `type: Learning Element`.

### 6.1 Frontmatter

```yaml
---
type: Learning Element
ptf_version: "0.1"
id: ptf:el/llm-basics/softmax          # REQUIRED
title: Softmax                          # REQUIRED
description: Turns arbitrary numbers into a probability distribution.   # REQUIRED
lang: en                                # REQUIRED, BCP 47
levels: [highschool, college, expert]   # REQUIRED, at least 2
tags: [llm, probability]
requires:                               # prerequisites (global IDs)
  - ptf:el/llm-basics/logits
leads_to:
  - ptf:el/llm-basics/cross-entropy
duration_min: { highschool: 10, college: 20 }
simulators:
  - ref: ptf:sim/next-char-lab@^2.0.0   # REQUIRED in each entry: ID + semver range
    station: counted-probabilities      # optional entry point
    levels: [highschool, college]       # where it fits
    role: explore                       # explore | practice | check
sources:                                # OKF provenance; grounding only
  - id: karpathy-gpt
    resource: https://www.youtube.com/watch?v=kCc8FmEb1nY
    title: "Let's build GPT: from scratch, in code, spelled out"
generated: { by: claude/opus, at: 2026-10-26T12:00:00Z }
verified: { by: "human:stefan", at: 2026-10-26T13:00:00Z }
status: draft                           # draft | reviewed | proven | deprecated
version: 1.0.0                          # semver of this element
license: CC-BY-SA-4.0
---
```

The full schema is [schemas/learning-element.schema.json](schemas/learning-element.schema.json).
Unknown keys MUST be preserved and MUST NOT cause rejection (OKF rule).

`status` values:

- `draft`: generated or written, not reviewed.
- `reviewed`: checked by a human for correctness.
- `proven`: reviewed, and learner data shows it works (§10).
- `deprecated`: kept for reproducibility; `superseded_by` SHOULD point to the replacement.

### 6.2 Body headings

The body uses these level-1 headings, in this order. Only `# Core` and
`# Misconceptions` are required.

| Heading | Required | Content |
| --- | --- | --- |
| `# Core` | yes | One or two sentences that are true at every level. |
| `# Key facts` | no | Numbers, definitions, formulas the tutor must get right. |
| `# Level: <id>` | no | A ready-made explanation for that level (§6.3). |
| `# Misconceptions` | yes | List of `**<id>**: <wrong belief> → <correct view>`. |
| `# Questions` | no | Question blocks (§7). |
| `# Examples` | no | Worked examples, code, calculations. |
| `# Further reading` | no | Optional deep-dive material for after the lesson (§6.5). |
| `# Sources` | no | Footnotes keyed to `sources` (OKF §5.1). |

Learner-facing text above `# Further reading` MUST NOT refer to the sources
("as shown in the video at 4:12"). Timestamps and similar belong in
`sources`, comments or `# Further reading`.

### 6.3 Level texts

Level texts are **optional**. Without them, the tutor composes an explanation
from Core, Key facts and Misconceptions. With them, the tutor MAY use the text
as is or adapt it to the learner.

- Each level text SHOULD start with something to try or guess, not with a
  definition.
- A level text MAY carry a version marker on the line below the heading:
  `<!-- ptf:text v2 -->`. Its ID is then
  `ptf:el/<bundle>/<name>#level/<level>@v2`, so learner feedback can be
  attributed to the exact text (§10).
- Translations MAY be added as `# Level: highschool (de)`. The canonical
  language of a bundle is given by `lang`; English is RECOMMENDED for
  shared libraries.

### 6.4 Misconception IDs

Each misconception has a short ID (`softmax-makes-zeros`). Question blocks and
learner events refer to these IDs, which turns wrong answers into data about
where learners stumble.

### 6.5 Further reading

`# Further reading` lists material a learner MAY explore after the lesson,
for example the video or paper the element was grounded in. It turns
sources into an optional deep dive without making the lesson depend on
them:

- The element MUST be complete without it. A tutor offers it only once the
  learner has worked through the element, or asks for more.
- Each entry is a list item with a Markdown link, a one-line description of
  what the learner will get from it, and optionally a timestamp range or
  section and a level hint:

  ```markdown
  - [Let's build GPT: from scratch, in code, spelled out](https://www.youtube.com/watch?v=kCc8FmEb1nY&t=3720s):
    builds a self-attention head in PyTorch step by step (video, 1:02–1:20; college).
  ```

- Links SHOULD point to stable, freely accessible resources. Hosts show
  them as ordinary links outside any simulator sandbox.

## 7. Question Blocks

A question block is a JSON object inside a fenced code block with the info
string `ptf-question`, under `# Questions`. It MAY instead live in a separate
file `questions/<element>.json` holding an array of blocks.

Common fields (all kinds):

| Field | Required | Meaning |
| --- | --- | --- |
| `kind` | yes | One of the kinds below. |
| `id` | yes | Unique within the element. |
| `level` | yes | Level ID. |
| `purpose` | no | `warmup` (guess before learning), `check` (understanding, default), `transfer` (apply in a new situation). |
| `misconception` | no | Misconception ID this item targets. |
| `explanation` | yes | Why the answer is right, shown after answering. |

Kinds in v0.1 (field details in [schemas/question-block.schema.json](schemas/question-block.schema.json)):

| Kind | Learner does | Specific fields |
| --- | --- | --- |
| `multiple_choice` | Picks one or more options | `question`, `options[{text, correct, feedback}]` (3 to 5) |
| `guess_next` | Guesses the next character, word or number | `intro`, `prefix`, `answer`, `accepted[]`, `hint` |
| `cloze` | Fills 2 to 5 gaps marked `{{1}}` … | `text`, `gaps[{answer, accepted[]}]` |
| `estimate_number` | Estimates a value | `question`, `answer`, `tolerance`, `unit` |
| `ordering` | Puts 3 to 7 items in order | `instruction`, `items[]` (correct order) |
| `calculation_steps` | Follows or completes a worked table | `title`, `intro`, `columns[]`, `rows[][]`, `result{label, value}` |
| `free_text` | Answers in their own words | `question`, `rubric[]`, `sample_answer` |

Example:

```ptf-question
{
  "kind": "multiple_choice",
  "id": "q1",
  "level": "highschool",
  "purpose": "check",
  "misconception": "softmax-makes-zeros",
  "question": "The scores are [2, 1, 0]. What is true after softmax?",
  "options": [
    { "text": "The values add up to 1", "correct": true, "feedback": "Yes, softmax normalises." },
    { "text": "The smallest value becomes 0", "correct": false, "feedback": "No: e^0 = 1, so it stays positive." },
    { "text": "The order of the values can change", "correct": false, "feedback": "No: softmax is monotonic." }
  ],
  "explanation": "Softmax computes e^x for each score and divides by the sum."
}
```

The kinds follow the generative-UI catalog principle (json-render, OpenUI):
a model fills in a known component; it does not invent UI. Hosts render each
kind with their own components.

## 8. Learning Path

`type: Learning Path`, one file per path.

```yaml
---
type: Learning Path
ptf_version: "0.1"
id: ptf:path/llm-basics/gpt-from-scratch
title: How GPT works, from scratch
description: Eight steps from "predict the next character" to a transformer.
lang: en
goal: Understand how a GPT-style model is trained and generates text.
audience: [highschool, college]
steps:
  - element: ptf:el/llm-basics/tokenizer
  - element: ptf:el/llm-basics/softmax
  - element: ptf:el/llm-basics/cross-entropy
    optional: false
status: draft
version: 0.1.0
---
```

The body MAY describe the path in prose, list planned steps that have no
element yet, and give the tutor guidance (typical pace, where learners
usually need a break).

## 9. Versioning

- Learning elements, paths, bundles and simulators carry a `version` in
  [semver](https://semver.org).
- **Simulator versions are immutable.** A published `sims/<name>/<version>/`
  directory MUST NOT change. Fixes are new versions.
- Content refers to simulators by **range** (`^2.0.0`, `~1.2.0`, `2.1.3`).
- A bundle MAY pin exact versions in `ptf.lock`:

```json
{
  "lockfileVersion": 1,
  "simulators": {
    "ptf:sim/next-char-lab": { "version": "2.0.0", "integrity": "sha256-…" }
  }
}
```

- A host or tutor SHOULD use the locked version when present, so a lesson
  repeated later shows exactly the same simulator. It MAY propose a newer
  minor or patch version within the range, and MUST ask before moving to a
  new major version.
- Simulator semver rules are in SIMULATOR-SPEC.md §3.

## 10. Feedback into the library

Learner records stay private (LEARNER-RECORD.md). What MAY flow back into a
library is **aggregated and anonymous**:

- per misconception ID: how often it occurred;
- per level text version: how often learners continued with "understood"
  versus "explain differently", and how they did on the following questions;
- per simulator version: error reports.

A library MAY record this under `stats` in frontmatter, or in a separate file.
It is the basis for promoting content to `status: proven` and for replacing
weak level texts.

## 11. Conformance

A PTF v0.1 bundle is conformant if:

1. It is a conformant OKF v0.2 bundle (every concept file has frontmatter
   with a non-empty `type`).
2. `index.md` has `type: Bundle` and `ptf_version`.
3. Every `type: Learning Element` file validates against
   `schemas/learning-element.schema.json` and has the headings `# Core` and
   `# Misconceptions`.
4. Every `ptf-question` block validates against
   `schemas/question-block.schema.json`.
5. Every `simulators[].ref` resolves to an existing simulator version.
6. Every simulator package validates against SIMULATOR-SPEC.md §2 and its
   `integrity` matches its files.

`tools/ptf-check` checks all of these.

Consumers MUST tolerate unknown `type` values, unknown keys, unknown levels
and missing optional sections.

## 12. Prior art

| Format | What PTF takes from it |
| --- | --- |
| Open Knowledge Format (OKF) | Bundle structure, frontmatter, provenance and trust fields, tolerance rules |
| SCORM, cmi5 | Packaged content that runs embedded and reports progress |
| xAPI | Actor–verb–object vocabulary for learner events |
| H5P | Separation of content type (code) and content (parameters); per-library versions |
| IMS QTI 3.0 | Question kinds and scoring vocabulary (export target) |
| OpenStax / CNXML | Small reusable modules composed into paths; open licensing |
| PhET-iO | A stable host API for simulations: state, events, external control |
| MCP Apps (SEP-1865) | Sandboxed HTML views talking JSON-RPC over postMessage |
| json-render, OpenUI | Catalog of typed components instead of free-form generated UI |
| npm / semver | Names, version ranges, lockfiles, integrity hashes |
